- [ ] to:grok-wire from:coordinator TOP PRIORITY, ROOT CAUSE of Ubuntu low per-peer throughput, mid-run decay and the peer-count gap. Measured: Go ~4.8 MiB per active peer per minute, Rust ~0.9 (5x lower). Cause: Rust's per-peer rate is NOT Go's. Go peer.go:187 downloadRate() = BytesReadUsefulData / totalExpectingTime(). totalExpectingTime (peer.go:268) accumulates ONLY the time with outstanding requests (cumulativeExpectedToReceiveChunks + time since lastStartedExpectingToReceiveChunks), over the whole connection. Rust stats.rs RateEstimator is a wall-clock EMA (alpha 0.25 over >=100 ms windows) updated only in add_bytes, so after any idle gap one 16 KiB block / long elapsed crashes the rate. Feedback loop: webtor pipeline limit = rate*rtt*2/16KiB + 2 shrinks, then more gaps, then lower rate (= mid-run decay). The same collapsed rate drives SlowPeerYield (peer_conn.rs ~1086), HOL/hedge/steal comparisons (~1127, ~1157, hol.rs, decisions.rs) and slow/idle peer drops, so peers look slow, lose requests, idle and get dropped (= fewer peers). Fix: (1) port Go exactly: add expecting-time accounting to the per-peer state: start the clock when outstanding requests go 0 -> >0, stop it when they go back to 0 (and on choke/close, as Go does in updateExpectingChunks), count useful bytes only, rate = useful/expecting. Use it everywhere Go uses downloadRate(): pipeline limit, SlowPeerYield, HOL/hedge/steal, arrival model, Ghost/stats views. (2) RttEstimator default estimate must be 0 like Go (no playback pipeline cap until the first real sample; Rust starts at 200 ms). (3) nominal_max: Go has no 128 ceiling; it is min(PeerMaxRequests from LTEP reqq, peak*2, maxLocalToRemoteRequests ~ (writeBufferHigh-low-5)/17). Replace NOMINAL_CEILING=128 with Go's bound (if you need a safety cap, use reqq clamped to 2048).
